## 未解決の不具合

### Chrome の特定の窓口だけ `file is not a database` になる（原因は未特定）

2026-08-02 と 2026-08-19 の2回、実機で発生。**原因は分かっていない。**
公開の関門からは外してあり、**公開後もそのまま残っている。**

症状は `SQLite: file is not a database`。Chrome の特定のウィンドウだけで起き、
シークレット・Firefox・Vivaldi では正常。**Ctrl+Shift+R では直らず**、
キャッシュ削除で直る。Vivaldi も Chromium なので**エンジンではなくプロファイル固有**。

#### 2026-08-19 の実測（前回の見立てが1つ崩れた）

- **落ちたのは 2026H2 の1本だけ。** 他11期間は `constructed vfs` まで通っている。
  `search()` は `Promise.all` なので、**1本落ちると検索全体が失敗する**
- **`&retry=1` `&retry=2` も走っていて、どちらも同じく失敗した。**
  URLが違えばキャッシュエントリも別なので、**「壊れたブラウザキャッシュ」説はここで消えた。**
  あの窓口がネットワークから受け取ったバイト列自体が壊れていたことになる
- **R2 は無実**（3回目）。同じ Chrome の別タブから12本すべて、HEAD の Content-Length・
  先頭16バイト・`page_size` を確認。通常の fetch と `cache: "reload"` で同じバイト列。
  同じタブで `/search?q=リポスト` は 1691ms で20件返る
- **唯一の構造的な差**: 2026H2 だけ `Content-Type` が付いていなかった。
  それは 8/18 の日次が置き換えた唯一のファイルで、`daily.yml` が `--content-type` を
  渡しておらず**ランナーの mime データベース任せ**になっていたため
  （8/12 に上げた11本には `application/vnd.sqlite3` が付いていた）。
  → 固定済み。**ただしこれが原因である証明は無い**（同じURLを別タブから20回引いて
  20回とも正常だった）

潰した容疑者: R2 の配信（無実）、期間DBの中身（無実。12本ともヘッダ正常・サイズ一致）、
`accept-ranges` が CORS で公開されていないこと（**原因ではない**。配布物を読むと
この値は警告を出すだけで取得の仕方を変えていない。R2 は実際には返している）、
**ブラウザキャッシュ**（2026-08-19 に否定。別URLでも落ちる）。

対処として `immutable` を外し（再読み込みで治るようになった）、
やり直しに `&retry=` を足してURLを変えるようにした。
配信側を壊す再現（`POISON=1`）では自力で復旧したが、
**実機の再発はこれでは救えなかった**＝本物の壊れ方を再現できていない。

#### 再発したら見るもの

**キャッシュを消す前に。** 消すと次の再発まで何も分からなくなる。

1. **Console に `<期間> の先頭16バイト` が出ている**（`site/src/lib/db.ts` の
   `reportBadHeader()`）。`cached`（ブラウザキャッシュ経由）と `network`
   （`cache: "reload"`）の両方が出るので、**どちらが壊れているかがその場で分かる。**
   ゼロ埋めか・HTMLか・別の世代のDBかも、ここで分かる
2. **`gh run list --workflow=daily.yml`。** 「配ったものを公開URLごしに検算する」が
   落ちていれば**サーバ側**（`scripts/verify_published.py`）。緑ならサーバは正常
3. 手元からも同じ検算ができる:
   `python scripts/verify_published.py --base https://db.kokkai-timeline.com`
4. **どの期間が落ちているか**を控える（`<期間> のDBを読み直す` に出る）。
   日次が毎日差し替えるのは当期の1本だけなので、そこに寄っているかは意味がある

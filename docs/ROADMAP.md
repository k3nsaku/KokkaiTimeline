## 1. 争点語・頻出語を主機能に寄せる

方針の理由は [DECISIONS.md](DECISIONS.md) の「争点語・頻出語を主機能にする」。
**A〜E すべて実装済み**（2026-08-07）。
A（半角→全角）・B（2文字の全角ラテン）・C（頻出語レイヤー）・
D（会期での絞り込み）・E（導線の入れ替え）。
**どれも全年DBの作り直しが要らなかった**ので、公開したまま順に足せた。

### ~~C. 頻出語レイヤー~~ — 済（2026-08-06）

`scripts/build_frequent.py` → `data/dist/frequent.json`（500語・138KB）。
サイトは `/frequent`（一覧）と `/word/<語>`（推移＋発言一覧）で、
**全年DBの作り直しは不要**。検索は既存の `word_hit` / FTS にそのまま流している。
落とし穴は [PITFALLS.md](PITFALLS.md) の「頻出語」。

実測して決めた値:

- **語数は500。会派の内訳は付けなかった。** 500語×20会派×64月で**1.6MB**になる
  （語だけなら115KB）。必要になったら**別ファイル**にして上位数十語だけ付ける
- **並びは burst**（ピーク年 ÷ 中央値の年）。頻度順は `国務大` `日本` `重要` `関係` で
  埋まって使えない（実測）
- **走査は約1分**（512,247発言）。日次に足してある
- ページ上で「運営が選んだ争点語」と「機械抽出の頻出語」は明示的に分けた。
  両方にある11語は争点語ページへ寄せている

### ~~D. 任意期間（月・会期）の抽出~~ — 済（2026-08-06）

`/frequent` に会期のセレクタを付けた。選ぶと**その会期でいつもより多く出た語**が
出る（倍率 ＝ その会期の出現率 ÷ 全期間の出現率）。**DBは引かない。**
判定は `site/src/lib/frequent.ts`（純粋関数・テスト14件）。

計画から変えたのはここ:

- **会期を「月の合算」で作らなかった。** 会期は月境界で始まらない
  （第204回は 2021-01-18 開会で、同じ月に第203回が同居する）。
  月を足すと境目の発言が隣の会期に混ざるので、`build_frequent.py` が
  **会期ごとに直接数える**。500語×11会期で +23KB しか増えない
- **日付の自由入力は入れなかった**（計画どおり）。会期だけで足りる
- **発言の少ない会期は選べない**（既定 3,000件未満。第220回は191件しかなく、
  並べても首班指名の手続き語しか出ない）。19会期のうち11会期を載せている
- ブラウザから `word_hit` / FTS で範囲集計はしていない（計画どおり。
  やると全走査になる）

### ~~E. 導線の入れ替え~~ — 済（2026-08-07）

トップの節の順序を組み替えた。**検索窓は消していない**（節の1つに降ろした）。

```
急増語 → 争点語 → 頻出語 → 検索 → 議員 → 収録しているもの
```

- **議員の節に「発言数の多い順」を置かない。** トップに並べると事実上の議員評価になる
  （[SCOPE.md](SCOPE.md)）。人数と一覧への導線だけ出し、**並べない理由もページに書いた**
- 各節に「それが何であるか」を1行で添えた。争点語は「運営が選んだ82語」、
  頻出語は「運営が語を選んでいない500語」と、**層の違いをトップの時点で明示する**
- 検索の節に「検索語はどこにも送られない」を出した。ここが差別化でもあるので、
  降ろした代わりに性質を書く

## 未解決の不具合

### Chrome でブラウザキャッシュが壊れると全ページが落ちる（原因は未特定）

2026-08-02 に実機で発生。**原因は分かっていないが、「一度壊れると永久に直らない」
性質のほうを消した**ので、公開の関門からは外した。**公開後もそのまま残っている。**

症状は全ページで `SQLite: file is not a database`。Chrome の通常ウィンドウだけで起き、
シークレット・Firefox・Vivaldi では正常。**Ctrl+Shift+R では直らず**、
キャッシュ削除で直る。Vivaldi も Chromium なので**エンジンではなくプロファイル固有**。

潰した容疑者: R2 の配信（無実。冷えたキャッシュでも 206 を 49ms で正しく返す）、
年DBの中身（無実。6年ともヘッダ正常・サイズ一致）、
`accept-ranges` が CORS で公開されていないこと（**原因ではない**。配布物を読むと
この値は警告を出すだけで取得の仕方を変えていない）。

対処として `immutable` を外し（再読み込みで治るようになった）、
やり直しに `&retry=` を足してURLを変えるようにした。
配信側を壊す再現（`POISON=1`）では6年すべてが自力で復旧するが、
**実機の再発はこれでは救えなかった**＝本物の壊れ方を再現できていない。

**再発したら、キャッシュを消す前にこれを見ること:**

1. **Console に `年のDBを読み直す` が出ているか** — 出ていれば再試行は走っている
   （＝別URLでも壊れたものが返る。キャッシュ以外の要因）
2. **Network タブの `kokkai-*.db` の Size 列。** `(disk cache)` ならブラウザキャッシュ由来。
   `retry=` 付きのURLが並んでいるかも見る
3. **`cache-control` に `immutable` が残っていないか**

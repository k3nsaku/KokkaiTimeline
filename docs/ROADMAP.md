## 2. 最大の未検証リスク → ✅ 解消（2026-08-01）

> ### ✅ sql.js-httpvfs は 350MB のDBで実用速度を出せる。退避案は使わない
>
> 実測は **`docs/PHASE1_PROTOTYPE.md`**。計測コードは `prototype/`。
> 典型的な検索 **1.5〜2.5秒** / 議員ページ **1.1秒** / 前後表示 **0.24秒**
> （Cloudflareエッジまでの実測RTT 19.6ms を注入した値）。

**ただし守らないと破綻する制約が3つある。実装前に必ず読むこと。**

| 制約 | 守らないとどうなるか |
|---|---|
| **「新しい順」は `ORDER BY rowid DESC`。`date` で並べない** | 検索で **204MB** 転送、議員ページで **7,800リクエスト** |
| **年またぎは年ごとに別ワーカで並列。ATTACH+UNION にしない** | 待ち時間が年数に比例（6年で13秒前後） |
| **配信するDBを WAL にしない** | `-wal` が要るのでブラウザから開けない |

`page_size` は **8192**（＝`requestChunkSize`）を採用。
4096 比でリクエスト18%減・DBサイズ4%減。16384以上は転送量が増えすぎる。

**残りの未検証**: 実際に R2 に置いたときの CDN キャッシュのヒット率と RTT。
Cloudflare アカウントが要るため未実施。ただし待ち時間は
「リクエスト数 × RTT」でほぼ決まると分かったので、RTT さえ測れば予測できる。

> 参考: 実用にならなかった場合に用意していた退避案（**現時点では不要**）。
> ① 会期ごとの分割 ② 直近N年に絞る ③ 転置インデックスを静的JSONで持つ
> ④ Cloudflare Workers + D1（「常時稼働を持たない」制約に触れるので最終手段）

## 4. 未解決の課題

### 4-1. 2文字の検索語が引けない → ✅ 解消（2026-08-02）

**任意の2文字語を直接引けるようになった。** `word` / `word_hit` テーブル
（語彙 16,058件・`scripts/build_words.py`）。争点語リストに載っている必要はない。

一度は `topic_hit` で「争点語に入っていれば引ける」状態にしたが、
**検索できる語を増やすために `topics.json` を膨らませるのは筋が悪い**。
あれは「何を争点として扱うか」という編集方針であって、検索の索引ではない。
そこで機械抽出の語彙を別に持つことにした。

| | topic | word |
|---|---|---|
| 何 | 争点語79件。運営の編集方針 | 2文字語16,058件。機械抽出 |
| 用途 | 頻度推移・会派比較 | 2文字語を引けるようにするだけ |
| 一覧表示 | する（`/topics`） | しない |

実測（`data/dist/kokkai-2025.db`）:

| | |
|---|---|
| 語彙 | 16,058件（全期間で**自立して5件以上**の発言に出る2文字語） |
| 索引の行数 | 1年あたり約330万行（2025年で 3,255,905） |
| **DBサイズ** | 374.9MB → **409.7MB（+9.3%）**。全体で 1.91GB → **2.09GB**（R2無料枠の21%） |
| 索引の構築 | 1年あたり **21秒**（年DB全体で45秒） |
| 引く速さ | 先頭20件を **0.2ms**（ローカル・一時B-TREEなし） |
| 正しさ | `instr(body, 語)` の全走査と件数が**完全一致**（憲法1,369 / 年金2,175 / 増税314 ほか） |

**語彙の選び方と索引の作り方で数え方が違う。** 語彙は「ちょうど2文字で自立している」
箇所だけを数え、索引は**部分文字列**で拾う（「憲法改正」の中の「憲法」を引けないと
検索として意味がない）。詳細は `CLAUDE.md` の「2文字語」。

残る穴:

- **ひらがなだけの2文字語は引けない**（語彙が漢字とカタカナの連続しか見ていない）
- 自立して5件未満の語は引けない。引けなかったときは
  **その旨と、その語を含む争点語**を出すようにしてある（黙って0件にしない）

以下は当時の記録。

<details><summary>元の課題（展開）</summary>


trigram は3文字未満のトークンを作れないため、**「増税」「憲法」「年金」「原発」が
検索結果0件になる**。日本語の政治キーワードは2文字が非常に多い。

| 語 | FTS `MATCH` | 実際に含む発言 |
|---|---:|---:|
| 増税 | **0件** | 18件 |
| 憲法 | **0件** | 189件 |
| 年金 | **0件** | 733件 |

※ 2025年6月の1か月分での計測

これは企画書の「争点別スタンス比較」「キーワード頻度推移」と実装が重なるので追加コストは小さい。

本文はDBにあるので `LIKE '%増税%'` というフォールバックも一応使えるが、
全走査になるため sql.js-httpvfs 経由では現実的でない。

### 4-2. Wikidata に項目が無い議員がいる

現在9人（2,217発言 / 全体の0.4%）。うち6人は2026年初当選の新人で、
Wikidata の項目作成が追いついていないだけ。**恒久的な欠落ではない。**

対応方針は決まっている: **Wikidata ID は必須キーにせず補助キーにする。**
会議録側の情報だけで独自IDを振り、日次の再突合で項目ができた時点で自動的に紐づける。

### 4-3. 会派 → 政党の対応表は手動メンテが必要

新しい会派が出るたびに `data/party_map.json` への追記が要る。
`match_politicians.py` が未登録を警告するので気づけるが、自動化はされていない。

2026年だけで5件の新会派が登場した（`中道改革連合・無所属` `チームみらい` など）。
選挙のたびに増えると考えてよい。**月1時間の運用工数のうち、ここが主な消費先になる見込み。**

### 4-5. 候補が1つの会派は自動確定するのでレビューを通らない → ✅ 対処済み

`party_map.json` の候補が1件の会派は機械的に確定するため、手入力リストに出てこない。
ほとんどは会派名＝政党名で問題ないが、**会派名が政治団体名で、構成員の政党が違う**
ケースがあった。

| 会派 | 議員 | 発言 | 確定した政党 | Wikidata の政党(P102) |
|---|---|---:|---|---|
| みんなの党 | 渡辺喜美 | 130 | みんなの党 | 自由民主党 / **みんなの党** |
| みんなの党 | 浜田聡 | 232 | **NHKから国民を守る党** | みんなでつくる党 / **NHKから国民を守る党** ほか |

浜田聡はNHK党系で、会派名の「みんなの党」は渡辺喜美側の党名だった。両方を入れた:

1. `party_map.json` の `みんなの党` の候補に `NHKから国民を守る党` を追加
   → 会派の実態が「2政党の統一会派」として表現され、以後この会派に別の人が
     現れても自動確定せず手入力リストに載る
2. `party_overrides.json` に浜田聡の項目を追加
   → 人が決めた事実を固定する（Wikidata の P102 が変わっても揺れない）

なお `ＮＨＫ党` `政治家女子48党` `ＮＨＫから国民を守る党` はすべて政党
`NHKから国民を守る党` に寄せてある。**改称ごとに分けると同じ党の発言数が割れる。**

> 自動確定分1,613件をWikidataのP102と突き合わせると115件が食い違うが、
> **ほぼ全部がP102側の古さ**（会派「立憲民主党・無所属」の安住淳のP102が『民主党』など）。
> 会派名から決まる分のほうが確実なので、この食い違いは追わなくてよい。

### 4-7. DBを差し替えると開きっぱなしのページが壊れる → ✅ 対応済み（2026-08-02）

日次更新で当年のDBを置き換えると、そのとき開いていたページが
`no such table: speech_fts` のような形で落ちる。`sql.js-httpvfs` は読んだページを
**オフセットで覚えている**ので、裏でファイルが変わると
「古いページと新しいページが混ざったDB」を読むことになる。
検証中に実際に何度も踏んだ。

対応は2段:

1. **DBのURLに世代を入れる。** `manifest.json` の `version`（中身のsha256の先頭16桁）を
   `?v=` で付ける。中身が変われば別のURLになるので、新しく開いたページは取り直し、
   古いURLはエッジに残ったまま中身が揃う。**CDNのパージも要らなくなる**ので、
   DBは `immutable` で配れる（短くするのは `manifest.json` だけ）。
   指紋の計算は2.09GBで **2.0秒**。
2. **保険。** 問い合わせが失敗したら目録を取り直してワーカを作り直し、**1回だけ**やり直す。

### 4-6. 発言ページの OGP は共通のものしか出せない

発言は 650,785 件あって事前生成できない。`/speech/<id>` は1枚の静的HTMLを
200 rewrite で使い回しているので、**OG画像も説明文も全発言で同じ**になる。
SNSでの見え方は「サイト名だけ」に近い。

`whatiwant.md` の「SNSシェアの導線」としては弱い。解決するなら発言ページだけ
Workers で動的にOGPを返すことになるが、**「常時稼働プロセスを持たない」制約に触れる**。
共有が実際に伸びないと分かってから考える。それまでは静的のまま。

| 決定 | 理由 | 節 |

| sql.js-httpvfs で進む | 350MBのDBで典型的な検索1.5〜2.5秒。退避案は不要 | P1 §1 |

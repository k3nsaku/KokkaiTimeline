## 1. 次にやる改善

上から順に着手する。新機能より先に公開フローを安全にし、利用状況を見てから
機能の優先順位を決める。

### A. 日次更新を公開前に検証する

現在の `daily.yml` は期間DBと目録を R2 に上げたあとでサイトをビルドし、
Pages へ公開したあとで議員ID台帳を `git push` する。途中で失敗すると、
公開物だけが先に進む可能性がある。

- [ ] R2・Pages の公開前に `npm run check` と `npm run build` を終える
- [ ] 作り直した期間DBに `PRAGMA quick_check` を掛け、`meta` と目録の期間・分割規則も照合する
- [ ] FTS・2文字語・争点語の3経路を代表語で1件ずつ引くスモークテストを置く
- [ ] 議員ID台帳に差分があるときは、外部への公開より前に commit / push する

完全な同時更新はできないが、**検証に落ちたものを公開しない**順序にはできる。
目録をDBより後に上げる原則と、URLの `?v=` による世代分離は維持する。

### B. 匿名アクセス解析を入れる

目的は検索語や個人の追跡ではなく、次に直す場所を決めるための集計に限定する。

- [ ] `/search`・争点語・頻出語・議員・会期の、ページ種別ごとの利用比率を見る
- [ ] モバイル比率と Core Web Vitals を見る
- [ ] **検索URLのクエリ文字列を収集しない**ことを導入時に公式仕様で再確認する
- [ ] `site/src/lib/operator.ts` の `analytics` と `/privacy` を同じ変更で更新する
- [ ] まず2〜4週間だけ観測し、その結果で次の機能の優先順位を決める

候補は Cloudflare Web Analytics。2026-08-15 時点ではクエリ文字列を記録しないが、
将来の変更可能性が[公式FAQ](https://developers.cloudflare.com/web-analytics/faq/)に
書かれているため、導入時の再確認を必須にする。

### C. 会期と発言検索をつなぐ

`/session/<n>` でその会期に増えた語を見つけても、現在のリンク先は全期間の
`/topic`・`/word` で、会期の文脈がそこで切れる。新しい集計データは作らず、
既存の `meeting.session` で検索結果を絞る。

- [ ] `/search?q=防衛費&session=213` のように会期をURLへ保持する
- [ ] 検索画面に会期フィルターを足す
- [ ] 会期ページから「この会期の発言」へ進める導線を足す
- [ ] FTS・`topic_hit`・`word_hit` の結果取得3経路と件数3経路へ同じ条件を足す
- [ ] `countQuery()` では会期指定を「絞り込みあり」と判定し、絞り込み無しの高速経路を使わない。
      特に `word.n_speeches` の1行読みは黙って全期間の件数を返すので通さない
- [ ] 件数3経路でも `meeting` を JOIN し、`meeting.session` に同じ条件を掛ける
- [ ] 会期の `from` / `until` から対象の期間DBだけに絞り、無関係なワーカを立てない
- [ ] `frequent.json` に載っていない会期（発言3,000件未満など）を `session=` に
      直接指定されたときの扱いを決める。期間を特定できないまま全期間を引くか、
      「その会期は絞り込めない」と出すかを明示し、黙って0件にはしない
- [ ] 3経路 × 会期フィルターの回帰テストと、HTTP Range越しの性能計測を行う

会期条件はヒット索引から発言を絞るだけにし、`meeting.session` の索引追加は
実測で必要と分かるまで行わない。

## 未解決の不具合

### Chrome でブラウザキャッシュが壊れると全ページが落ちる（原因は未特定）

2026-08-02 に実機で発生。**原因は分かっていないが、「一度壊れると永久に直らない」
性質のほうを消した**ので、公開の関門からは外した。**公開後もそのまま残っている。**

症状は全ページで `SQLite: file is not a database`。Chrome の通常ウィンドウだけで起き、
シークレット・Firefox・Vivaldi では正常。**Ctrl+Shift+R では直らず**、
キャッシュ削除で直る。Vivaldi も Chromium なので**エンジンではなくプロファイル固有**。

潰した容疑者: R2 の配信（無実。冷えたキャッシュでも 206 を 49ms で正しく返す）、
当時の年DBの中身（無実。6本ともヘッダ正常・サイズ一致）、
`accept-ranges` が CORS で公開されていないこと（**原因ではない**。配布物を読むと
この値は警告を出すだけで取得の仕方を変えていない）。

対処として `immutable` を外し（再読み込みで治るようになった）、
やり直しに `&retry=` を足してURLを変えるようにした。
配信側を壊す再現（`POISON=1`）では当時の年DB6本すべてが自力で復旧したが、
**実機の再発はこれでは救えなかった**＝本物の壊れ方を再現できていない。

**再発したら、キャッシュを消す前にこれを見ること:**

1. **Console に `<期間> のDBを読み直す` が出ているか** — 出ていれば再試行は走っている
   （＝別URLでも壊れたものが返る。キャッシュ以外の要因）
2. **Network タブの `kokkai-*.db` の Size 列。** `(disk cache)` ならブラウザキャッシュ由来。
   `retry=` 付きのURLが並んでいるかも見る
3. **`cache-control` に `immutable` が残っていないか**

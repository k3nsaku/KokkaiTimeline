# 決定と、その理由

**判断を蒸し返す前にここを見る。数字はすべて実測値**で、推測ならその旨を書いてある。
いまどうなっているかは [ARCHITECTURE.md](ARCHITECTURE.md)。

計測環境は Windows 11 / Python 3.12 / Node 24 / SQLite 3.49.1（DB構築）・
3.35.0（sql.js-httpvfs 同梱）。ブラウザ側の計測は 2025年DB（約390MB）に対して、
Cloudflare エッジまでの実測RTT（19.6ms）を注入して行った。

---

## 1. 全体

### 一次資料しか扱わない。報道記事は集めない
著作権リスクを避けられて、かつ差別化になる。争点キーワードの抽出も
**国会会議録だけで十分機能する**ことを実証したので、外部ソースは要らなかった
（2021年6月と2025年6月を比べると、`暫定税率` 0→346・`物価高` 0→210 のように
その年の争点がそのまま出た。逆に `蔓延防止` 90→0・`無観客` 46→0）。

### サーバーを持たない（完全静的サイト）
個人運営が破綻する原因は「サーバー代」と「常時稼働プロセス」なので、両方を消す。
壊れても数日放置できる形にしておく。

### 独自の点数付け・ランキング・議員の評価をしない
公職選挙法・名誉毀損リスク。詳細は [SCOPE.md](SCOPE.md)。

### 争点語・頻出語を主機能にする（2026-08-03）
NDL の国会会議録検索システムとは**収録範囲で勝負にならない**（こちらは2021年〜、
NDL は1947年〜）。網羅性では原理的に負ける。一方 NDL に無いのは
「いつ・どの会派が・どれだけその語を使ったか」で、そこは既に持っている。
**手持ちの資産で差別化できる方向に寄せる。**
検索は入口の1つに降ろすが、**既存機能は消さない**（情報の順序で表現する）。

### 収録は2021年1月以降のまま
2012年まで遡ると R2 の使用量が 3.3GB → 約8.1GB になり、無料枠10GBの余裕が消える。
遡らなければ**年あたり約620MBの増加で10年もつ**。技術的には可能
（+100万件 / DB +3GB / 取得14.5時間）だが、得るものが釣り合わない。

## 2. 保存と配信

### DBは Cloudflare R2 に置く
| プラットフォーム | 制約 |
|---|---|
| Cloudflare Pages | **1ファイル 25 MiB 上限** → DBを置けない |
| GitHub リポジトリ | 1ファイル 100 MB 上限 → コミットできない |
| **Cloudflare R2** | 10GB 無料・**egress無料**・`GetObject` は Class B で月1,000万リクエストまで無料 |

1検索あたり平均80リクエストなので、**月12万検索まで無料枠に収まる**。
リクエスト数は制約にならない。

### Vercel を使わない
帯域課金がある。バズると個人の財布が痛む。

### DBは年ごとに分割する
日次更新で変わるのは当年だけなので、過去年は CDN に載ったまま再アップロードが要らない。
「議員 × キーワード × **期間**」という検索の形とも噛み合う。

### `page_size = requestChunkSize = 8192`
`requestChunkSize` は page_size と一致させるのが最適だった。小さいと1ページの
読み出しに複数リクエストが要り、大きいと読み過ぎで転送量だけ増える。

| page_size（=chunk） | 4096 | **8192** | 16384 | 32768 |
|---|---:|---:|---:|---:|
| DBサイズ（2025年） | 375.3 MB | **358.9 MB** | 349.3 MB | 343.7 MB |
| 合計リクエスト | 859 | **707** | 596 | 496 |
| 合計転送量 | 3.6 MB | **5.6 MB** | 9.5 MB | 15.8 MB |

16384 以上はリクエストが1〜2割減るのに転送量が2〜4倍。帯域の細い回線では逆に遅くなる。

### 年DBに `immutable` を付けない（2026-08-02 に外した）
```
変更前: public, max-age=31536000, immutable
変更後: public, max-age=3600, s-maxage=31536000
```
`immutable` が付いていると、キャッシュが壊れたとき **Ctrl+Shift+R でも直らない**
（実際に1日で2回踏んだ。原因は特定できていないが、「一度壊れると永久に直らない」
性質のほうを消した）。**エッジは `s-maxage` で1年握るので CDN の効きは落ちない。**
中身が変われば `?v=` で別URLになるので、ブラウザ側を短くしても不整合は起きない。

### R2 に Cache Rule を入れる
Cloudflare は**拡張子でキャッシュ判定していて `.db` も `.json` も既定の対象外**。
カスタムドメインを付けただけでは効かない。

| | RTT 中央値 |
|---|---:|
| Cache Rule 前（`DYNAMIC`） | **77ms** |
| Cache Rule 後（`HIT`） | **8ms** |
| 初回（`MISS`） | 210〜260ms。**1回でオブジェクト全体がエッジに載る** |

待ち時間は「リクエスト数 × RTT」でほぼ決まるので、ここが約10倍効く。

> **無料プランのキャッシュ上限は1ファイル 512MB。** 最大は2022年の419MB。
> 超えた年DBは**黙ってキャッシュされなくなる**ので、近づいたら年ではなく会期で割る。

## 3. 全文検索

### FTS5 + trigram を使う
標準の `unicode61` は日本語を分かち書きできず機能しない。trigram なら形態素解析なしで
**3文字以上は完全一致**（誤検出・取りこぼしゼロ）になることを実測で確認した。

> bigram トークナイザは SQLite 標準に無く WASM の独自ビルドが要るので、
> 「壊れて困るものを作らない」に反する。採らない。

### `detail=full` 固定
インデックスを縮めようと `detail=column` / `detail=none` を試したが、trigram は
検索語をフレーズクエリに展開するため、**位置情報を落とすと4文字以上が検索不能**になる
（`phrase queries are not supported`）。サイズ削減はこの方向では諦める。

### 本文をDBに持つ（contentless FTS5 にしない）
**決め手はハイライトが必須要件だったこと。** 本文を持たない構成では
`snippet()` / `highlight()` が使えない。

サイズ差は5年で 1.28GB（本文なし）vs 2.15GB（本文あり）だが、
**本文を捨ててもさほど減らない**——本文なし 2,317B/件のうち **2,006B（87%）は
FTS インデックス**で、これは何をしても減らせない。しかもどの案でも R2 無料枠に収まる。
必須要件を犠牲にする理屈が立たなかった。

### 検索対象は議員の発言のみ。ただし全発言をDBに持つ
アプリの目的が「有権者が政治家について判断する材料の提供」だから。

| `speaker_kind` | 件数 | 割合 | 索引 |
|---|---:|---:|:---:|
| **議員** | 512,247 | 78.7% | ✅ |
| 政府参考人等 | 109,578 | 16.8% | — |
| 参考人 | 21,439 | 3.3% | — |
| 非発言（会議録情報） | 6,218 | 1.0% | — |
| 公述人 | 1,303 | 0.2% | — |

**参考人等もDBには残す。** 前後の文脈表示に使うし、後から索引を足すだけで
方針を変えられる。「議員のみ保持」との差は0.4GBで、無料枠に対して誤差。

閣僚答弁の取りこぼしはゼロ（大臣は議員なので `speakerYomi` を持つ）。

### 2文字語は専用の索引を持つ（`word` / `word_hit`）
trigram は3文字未満のトークンを作れない。**日本語の政治キーワードは2文字が非常に多い。**

| 検索語 | FTS `MATCH` | 実際に含む発言 |
|---|---:|---:|
| 増税 | **0件** | 18件 |
| 憲法 | **0件** | 189件 |
| 年金 | **0件** | 733件 |

※2025年6月の1か月分

一度は「争点語リストに載っていれば引ける」状態にしたが、
**検索できる語を増やすために `topics.json` を膨らませるのは筋が悪い**
（あれは編集方針であって検索の索引ではない）。機械抽出の語彙を別に持つことにした。

コストは **DBサイズ +9.3%**（1年で約330万行）。索引の構築は1年あたり21秒、
引くのは先頭20件で0.2ms。`instr()` の全走査と件数が完全に一致することを確認済み。

### 争点語リストにある語は FTS を使わない
`topic_hit` を引くほうが速い。2文字語対策として必須だったものが、
そのまま「よく引かれる語を事前計算して FTS を回避する仕組み」になっている。

| 引き方 | リクエスト | 時間 |
|---|---:|---:|
| 争点語「安全保障」 | 23 | **700ms** |
| FTS「安全保障」（同じ結果） | 76 | 2,308ms |

**同じ結果が3.3倍速い。**

### 遅いのはヒット件数ではなく検索語の長さ
trigram は N文字を N-2 トークンに展開し、そのすべての転置リストを突き合わせる。

| 語 | 文字数 | ヒット | リクエスト |
|---|---:|---:|---:|
| 原子力 | 3 | 795 | 52 |
| 安全保障 | 4 | 2,864 | 77 |
| デジタル田園都市国家構想 | 12 | 14 | **187** |

**ヒット14件の語が、ヒット2,864件の語の2.4倍遅い。**
事前の想定（ヒット数の多い語が最悪ケース）は外れていた。

> 長い語を切って FTS に投げ残りを `LIKE` で絞る緩和策を試したが、
> 5文字に切ると42%減る一方 **4文字に切ると10倍悪化する**。
> 切った語の選択性に完全に依存するので機械的に適用してはいけない。採用は保留。

## 4. 検索語の正規化

### 半角→全角に寄せる（NFKC は使わない）
**会議録は英数字を半角で1文字も書いていない。**

| 語 | 半角 | 全角 |
|---|---:|---:|
| `AI` | **0件** | `ＡＩ` 5,412件 |
| `Ｇ７` | **0件** | 4,439件 |
| `LGBT` | **0件** | `ＬＧＢＴ` 811件 |

利用者は普通に半角で打つので、そのままでは黙って0件になる。
寄せて失うものは無い——議員の発言 512,247件のうち**半角英字を含むのは54件（0.01%）**で、
中身は URL と英語の引用だった。

**★ NFKC を使ってはいけない。** NFKC は全角→半角に潰す**逆方向**の正規化で、
使うと全滅する。必要なのは `A-Za-z0-9` を `+0xFEE0` する片方向の写像だけ。

### 大文字に寄せるかは経路で逆になる
**ここを揃えようとすると必ずどちらかが壊れる。**

| 経路 | 畳むか | 理由 |
|---|---|---|
| **FTS** | **畳まない** | FTS5 の trigram が全角ラテンの大小を自分で畳む（実測 `ｌｇｂｔ` も `ＬＧＢＴ` も55件）。畳むと `ＳＤＧｓ` `ｉＰＳ` `ＩｏＴ`（全角ラテンの3.5%）が引けなくなるだけ |
| **word（2文字以下）** | **畳む** | `w.term = ?` は BINARY 比較で、SQLite の `NOCASE` も `upper()` も **ASCII 限定**なので全角に効かない。畳まないと `ai` が `ａｉ` になって語彙の `ＡＩ` に当たらず「引けない」と出る |

**畳むのは2文字以下だけ。** 3文字以上に掛けると `ＳＤＧｓ` → `ＳＤＧＳ` になって
本文に当たらない。捨てるのは2文字の全角ラテンで小文字を含む8語・69発言
（`Ｃｔ` `Ｍｙ` `Ａｉ` `ｐＨ` …）だけで、全部ノイズ。

### 2文字語の語彙に数字を入れる
`２０２１` から `２０` `０２` のような無意味な組が湧く懸念があったが、**実測で消えた**。
会議録は数字を漢数字で書くので、**全角数字だけの2文字語は全期間で1件も
`--min-df` に届かない**（2025年で `１０` を含む発言は 93,339件中1件）。
一方 `Ｇ７` は **4,439発言で `ＡＩ` に次ぐ2番目**に多い2文字ラテンで、捨てるには惜しい。

### 画面とURLは実際に引いた語に寄せる
`g7` と打って `ｇ７` と見せると嘘になるうえ、`?q=ｇ７` と `?q=Ｇ７` が
同じ検索の別URLになる。**利用者の入力を書き換えて表示してよい**と決めた
（「〜として検索した」と1行出す）。

## 5. 性能（ブラウザからDBを引く）

**結論: 350MBのDBで実用速度が出る。退避案には切り替えない。**
ただし守らないと破綻する制約があり、それは [PITFALLS.md](PITFALLS.md) に集めてある。

遅延20ms を注入した実測（page_size=chunk=8192）:

| シナリオ | リクエスト | 転送量 | 時間 |
|---|---:|---:|---:|
| DBを開くだけ | 1 | 8 KB | 0ms |
| 前後の発言（同一会議の5件） | 8 | 72 KB | 230ms |
| 議員ページ（直近50件・所属をJOIN） | 28 | 232 KB | 848ms |
| 検索 原子力（795件）新しい順20 | 52 | 424 KB | 1,610ms |
| 検索 安全保障（2,864件）新しい順20 | 77 | 640 KB | 2,341ms |
| 検索 デジタル田園都市国家構想（14件）★最遅 | 187 | 1,528 KB | 5,824ms |
| ✗ `ORDER BY date DESC` にした場合 | 114 | **189 MB** | 4,187ms |

同じ問い合わせの2回目は**すべて1〜5ms・リクエスト0回**（ページキャッシュがワーカ内に残る）。
**待ち時間はほぼ「リクエスト数 × RTT」で決まる。転送量は効いていない。**

R2 実機（Cache Rule 後・RTT 8ms）に置き換えると、争点語 0.17秒 / 議員ページ 0.22秒 /
FTS「安全保障」0.62秒 / 最遅ケース 1.5秒。**注入値での想定より速い。**

残る性質が2つある。**エッジごとに別々にキャッシュする**ので別地域の最初の利用者は
`MISS` を払う。**使われないオブジェクトは追い出される**ので、アクセスが少ない時期は
古い年のDBがコールドになりやすい。

### 年またぎは年ごとに別ワーカで並列に引く
sql.js-httpvfs はワーカ内で**同期XHR**を使うので、1ワーカ内のリクエストは必ず直列になる。

| 方式 | 時間 | 年数を増やすと |
|---|---:|---|
| **年ごとに別ワーカ → JS側でマージ** | **2.31秒** | ほぼ増えない |
| 1ワーカに ATTACH して UNION ALL | 4.42秒 | **年数に比例して増える** |

※2年分。単年が2.21秒なので、並列版は2年でも+0.1秒しか増えていない。
6年なら ATTACH 版は13秒前後になる見込みで実用にならない。

### sql.js-httpvfs は2022年から更新されていない
同梱の SQLite は 3.35.0。FTS5 も trigram も動くので現時点で困っていない。
将来必要になれば公式の `@sqlite.org/sqlite-wasm` に HTTP VFS を載せる余地がある。
**性能上の制約はライブラリによらず成立する**ので、乗り換えてもやり直しにはならない。

## 6. 名寄せ

**発言数ベースで 99.6% が一意に確定し、同姓同名の未解決は0件**（実人数1,102人）。
規模を55倍にしても確定率は落ちなかった。

| | 1か月 | 5か月 | **全期間** |
|---|---:|---:|---:|
| 議員の発言数 | 9,381 | 39,874 | **512,247** |
| 突合単位 | 447 | 1,018 | **1,803** |
| **確定率（発言数ベース）** | 99.5% | 99.5% | **99.6%** |
| 絞り込めなかった候補 | 0 | 0 | **0** |

### 突合の単位は `(発言者, 読み, 会派)`
読みだけだと**同姓同名が1行に潰れて原理的に分離できなくなる**。
会派を含めておくと政党移籍も自然に複数行として現れ、そのまま `affiliation` の材料になる。

### 読みが第一キー
会議録は「あべ俊子」「早稲田ゆき」のような通称を使う。
**漢字表記だけで突合していたらこれらは全部落ちていた。**
企画時点で最大の懸念だったが、`speakerYomi` で完全に解決できた。

### 同姓同名は会派で分離する。任期は使えない
| 信号 | 実測 |
|---|---|
| **会派 ↔ 政党(P102)** | **◎ 確実に分離できる** |
| 院 | **✕ 使えない**。大臣・副大臣は他院の委員会にも出るし、党首討論は `両院` |
| 任期(P580) | **✕ ほぼ効かない**。付与率が **13.7%** しかない |

当初は在任期間で分けるつもりだったが、データが無かった。会派のほうが強い信号だった。

### Wikidata ID は必須キーにせず補助キーにする
未マッチの9人（2,217発言 / 全体の0.4%）は突合ロジックの問題ではなく
**Wikidata 側にそもそも項目が無い**。うち6人は2026年初当選の新人で、恒久的な欠落ではない。
会議録側の情報だけで独自IDを振り、日次の再突合で項目ができた時点で自動的に紐づく。

### `party_map.json` を推測で埋めない
誤った対応表は同姓同名を**誤って分離する**ため、無記入より有害。
所属議員の Wikidata の政党(P102)を集計して決め、判断がつかない会派は空リストにする。

### 政党が不明な所属は NULL のままにする
推測で埋めるのは上と同じ害。集計の既定単位は会派にする。

## 7. サイト

### Astro を使う
中身の大半はクライアント側でDBから引くので、静的サイトジェネレータに求めたのは
**ページの事前生成**（議員1,111・争点語82。氏名で検索されたとき中身のあるHTMLを
返せるのはここだけ）と、**素の `<script>` をそのまま書けること**の2つだけ。
UIフレームワークは入れていない。**出力は静的HTMLなので Astro が壊れても公開中のサイトは動く。**

### ページ送りは rowid の keyset。OFFSET を使わない
OFFSET 80（5ページ目）が **134リクエスト・4.1秒**。keyset なら何ページ目でも1ページ目と同じ。

### 期間の絞り込みは年単位
年ごとに別DBを引く構成なので、年が絞り込みの自然な単位。年を減らすとそのぶん速くなる。
より細かい期間は月粒度＋会期で出す予定（[ROADMAP.md](ROADMAP.md)）。
**任意の日付範囲はやらない**——ブラウザ側の範囲集計が全走査になる。

### 発言ページの OGP は共通のものしか出せない
発言は650,785件あって事前生成できない。`/speech/<id>` は1枚の静的HTMLを
200 rewrite で使い回しているので、OG画像も説明文も全発言で同じになる。
解決するには Workers が要り、**「常時稼働プロセスを持たない」制約に触れる**ので、
共有が実際に伸びないと分かってから考える。

## 8. 運用

### `build_words.py` を日次で回さない
2文字語の語彙を当年だけ更新すると、**過去年の検索が黙って0件になる**。
語彙を作り直したら全年を作り直す（約6分）。安全網として年DBの `meta` に指紋を入れ、
食い違うとワークフローがその場で失敗する。

### `topics.json` を変えたら全年のDBを作り直す
壊れ方が語彙とは違う。語彙は「引けなくなる」だけだが、争点語は
**`topic_hit` の `topic_id` がずれる**ので `/topic/<id>` が**別の争点の発言を出す**。
語を1つ足すだけでも作り直すこと。

### NDL API のアクセス間隔を3秒より短くしない
NDL は「運用に支障があると判断した場合はアクセスを遮断することがある」と明記している。
遮断されたら詰む。全期間の取得は5時間17分で終わっており、これで困っていない。

### 争点語の候補は頻度上位ではなく増減で見る
頻度上位は「日本」「議論」「重要」で埋まる。年ごとの発言数が違うので割合に直してから比べる。
**両端（最初の年と最後の年）を比べない。ピーク年と中央値を比べる。**
両端比だと途中で山を作って収束した争点が消える（裏金は両端比2.4だがピーク比12.4、
マイナンバーは両端比0.2でピーク比4.6）。

### 争点語に地名を入れない
「沖縄」は6,305件あるが米軍との同時出現は23%で、残りは振興・観光。
会派比較すると「沖縄に言及した率」になって争点にならない。
基地問題は `辺野古`（`普天間` を `variants` で合算）で追う。「台湾」も同様に `台湾有事` にした。

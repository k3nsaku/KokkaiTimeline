# 踏んではいけない穴

**全部いちど実際に踏んだもの。** 同じ穴を掘り直さないために書いてある。
なぜそうなっているかの数字は [DECISIONS.md](DECISIONS.md)。

共通しているのは、**大半が「エラーを出さずに間違った結果を返す」**こと。
落ちてくれるものは自分で気づけるので、ここに載っているのはそうでないものが多い。

---

## NDL API

- **`REQUEST_INTERVAL_SEC`（3秒）を短くしない。** NDL は「運用に支障があると判断した場合は
  アクセスを遮断することがある」と明記している。遮断されたら詰む
- 検索条件がひとつも無いとエラー（19007）になる
- `Access-Control-Allow-Origin: *` を返すので**ブラウザから直接叩ける**

## 全文検索（FTS5 + trigram）

- **2文字以下の語は原理的に引けない。**「増税」「憲法」「年金」「原発」が全滅する
  → `word` / `word_hit`（2文字語の索引）で対応済み。下の「2文字語」を見ること
- **★会議録の英数字は全部全角。** DBに素の半角で問い合わせると0件になる
  （`AI` `DX` `LGBT` `TPP` すべて0件、`ＡＩ` は5,412件）。
  → 検索窓は `query.ts` の `toFullWidth()` で全角に寄せてある（`splitTerms()` が唯一の入口。
  ここを通れば FTS・争点語・2文字語の3経路とも直る）。**新しく引く経路を足すときも必ず通すこと**
  - **★NFKC を使わない。** 全角→半角に潰す**逆方向**の正規化で、使うと全滅する。
    やるのは `A-Za-z0-9` を +0xFEE0 する片方向の写像だけ
  - **★FTS 経路では大文字に寄せない。** trigram は全角ラテンの大小を畳むので幅だけで足りる
    （実測 `ｌｇｂｔ` = `ＬＧＢＴ` = 55件）。寄せると `ＳＤＧｓ` `ｉＰＳ` `ＩｏＴ` が引けなくなる。
    代わりに**突合とハイライトの側で畳む**（`matchTopic` と `highlightTerm`）
  - **★word 経路では逆に畳まないと引けない**（すぐ下の「2文字語」）
- **`detail=column` / `detail=none` は使えない。** trigram はフレーズクエリを使うため、
  位置情報を落とすと4文字以上が検索不能になる。`detail=full` 固定
- **`INSERT INTO speech_fts(speech_fts) VALUES('rebuild')` を使わない。**
  全行を索引化してしまう。議員だけを入れるには `SELECT ... WHERE speaker_kind='議員'` で入れる
- **`SELECT COUNT(*) FROM speech_fts` は索引件数にならない。**
  external content 構成では本体テーブルに委譲される。`speech` 側で数えること
- **SQLite 3.35 では `別名 MATCH ?` が使えない。** FTS5表に別名を付けても、
  MATCH は隠し列名（＝表名）で書く

## 2文字語

FTS5 の trigram は3文字未満のトークンを作れない。`word` / `word_hit` で対応している。

- **語彙リストは持たない。** 索引は本文に出てくる2文字窓を**部分文字列で全部**拾う
  （「憲法改正」の中の「憲法」を引けないと意味がない）。したがって
  **「その語を引けるか」を事前に判定する仕組みは無い**——索引に無い語は素直に0件。
  以前は `build_words.py` が作った語彙（16,264語）に載っている語しか引けなかった
- **語彙で索引を絞ろうとしない。** 実測（2026年DB）で全bigramにしても
  word_hit は 1.72倍・配布サイズは +7.3% にしかならない。
  語彙の裾（1発言にしか出ない語）は**語数の38%を占めて行数では1%**しか食わない
- **`word` の中身は期間ごとに違ってよい。** 検索は `w.term = ?` で引くだけなので、
  期間をまたいで揃っている必要がない。**この設計に変えたことで、日次更新で
  当該期間だけ作り直しても過去が黙って0件になる事故が起きなくなった**
- **`RUN_PATTERN` を片方だけ変えない。** `build_frequent.py` と `build_db.py` の
  `WORD_RUN_PATTERN` は同じものにすること。ずれると**一覧に出るのに検索できない語**が出る。
  現在は `[一-鿿々]{2,}|[ァ-ヴー]{2,}|[Ａ-Ｚａ-ｚ０-９]{2,}`
- **★この経路だけ全角ラテンを大文字に畳む**（`fold()` / `fold_word_run()` / `toWordKey()`）。
  **FTS 経路の「大文字に寄せない」と矛盾しない。** 別の経路の話で、理由も逆:
  `w.term = ?` は BINARY 比較で SQLite が畳まない（`NOCASE` も `upper()` も ASCII 限定で
  全角に効かない）。畳まないと `ai` が `ａｉ` になって索引の `ＡＩ` に当たらず0件になる。
  **畳むのは2文字以下だけ**（3文字以上に掛けると `ＳＤＧｓ`→`ＳＤＧＳ` で本文に当たらない）
- 複数語のときは**いちばん珍しい2文字語を起点**にして、残りは `instr()` で絞る。
  走査する行数が起点の語の件数で頭打ちになる。
  **起点を値で除外しない。** 畳んだ結果（`ＡＩ`）と打たれた語（`ａｉ`）は別物なので、
  値で比較すると起点が絞り込み条件にも残り、`instr()` が0を返して黙って全滅する
- **★2文字語 + 別の語の「件数」は起点の語の件数ぶん本文を読む。**
  実測で `安全保障 予算`（起点は `予算`）が **3,089リクエスト・946MiB**。
  `能登 復興` なら 168リクエスト・15MiB で済む。**結果の取得ではなく `countQuery()`**
  が重い（`instr(s.body, ?)` を全ヒットに掛ける）。未解決（`docs/DECISIONS.md`）
- **ひらがなだけの2文字語は引けない。** 索引が漢字・カタカナ・全角ラテンの連続しか
  見ていないため
- **語跨ぎの断片も引ける**（`務大`←国務大臣、`治体`←自治体）。索引なので害はないが、
  **一覧（`frequent`）には出さないこと**。あちらは「自立した run」で選んでいる

## ブラウザからDBを引く（sql.js-httpvfs）

数字はすべて 350MB のDBでの実測。根拠は [DECISIONS.md](DECISIONS.md) §5。

- **`ORDER BY date DESC` と書かない。`ORDER BY rowid DESC` にする。**
  date で並べると一時B-TREEができて**ヒット全件を読みに行く**。
  検索で **204MB 転送**、議員ページで **7,800リクエスト**になる。
  rowid は日付昇順に投入してあるので、結果は date 順と完全に一致する
- **月ごとに数えるときも `date` で GROUP BY しない。`rowid` の範囲で割る。**
  `substr(date, 1, 7)` でまとめると、当たった発言の**行を1件ずつ読みに行く**
  （実測・2025H1: `安全保障` 1.0ms → **170.6ms**、`風力発電` 0.4ms → 26.4ms）。
  月の先頭 rowid は `idx_speech_date` の seek で採れる（covering index だけで済み、
  `speech` の行は1件も読まない）。`monthlyQuery()` / `monthBoundsQuery()`。
  → **前提は「rowid の昇順 ＝ 日付の昇順」**。崩れると**件数は合ったまま月だけずれる**ので
  気づく手が無い。`verify_dist.py` の `check_monthly()` が毎回突き合わせている
- **絞り込み用のインデックスに `date` を足さない。** SQLite のインデックスは末尾に
  rowid が付くので、`speech(politician_id)` だけで `(politician_id, 日付)` 順になる。
  `(politician_id, date)` にすると rowid 順が保証されなくなり、上と同じ罠に落ちる
  （議員ページが 27リクエスト → **509リクエスト**）
- **配信するDBを WAL にしない。** `-wal` が本体の外に要るのでブラウザから開けない。
  `build_db.py` の `finalize()` が `journal_mode=DELETE` + `VACUUM` で畳んでいる
- **`db.query(sql, params)` の第2引数は配列で渡す。** 型定義は `(sql, ...params)` だが
  実体は sql.js の `exec(sql, params)`。展開して渡すと**黙って束縛されない**
- **wasm の URL は絶対パスで渡す。** ワーカ内で解決されるため相対パスだと壊れる
- **やり直しでは URL を変える（`&retry=`）。同じURLを引き直しても救えない。**
  閉じた期間のDBは差し替わらないので `?v=` も変わらず、**壊れたものが一度ブラウザ
  キャッシュに入ると、同じURLでは何度引いても同じものが返る**。
  再現は `POISON=1 node scripts/dev-data-server.js`
- **期間DBの `cache-control` に `immutable` を付けない。**
  付けると Ctrl+Shift+R でも読み直されず、利用者は手でキャッシュを消すまで直せない。
  配信は `public, max-age=3600, s-maxage=31536000`
- **ページ送りに OFFSET を使わない。** 5ページ目（OFFSET 80）で134リクエスト・4.1秒。
  `rowid < ?` の keyset なら何ページ目でも1ページ目と同じコストで済む
- **期間またぎのマージソートは要らない。だが連結もしてはいけない。**
  期間DBは日付で綺麗に分かれているので、新しい期間から順に並べれば全体が日付の降順になる。
  **ただし期間ごとに LIMIT を掛けている**ので、そのまま連結すると 20件のつもりが
  12期間ぶんで240件返り、しかも「いちばん新しい期間の21件目」を飛ばして次へ進む。
  → **全体で LIMIT 件に切り、1件も出さなかった期間はカーソルを進めない**（`mergePages()`）
- **分割の規則は2か所にある。** `build_db.py` の `period_of()` と `query.ts` の `periodOf()`。
  **片方だけ変えると存在しないファイルを引きに行く**（検索が丸ごと止まる）
- **期間IDは辞書順が時系列順**（`2021H1` < `2021H2` < `2022H1`）。並べ替えはこれに乗っている
- **2文字語の索引は期間ごとに違うので、件数のプローブは対象の全期間から引いて合算する。**
  1期間だけ見て起点（driver）を決めると、その期間にたまたま出てこない語で
  **他の期間まで0件になる**
- **件数の SQL に絞り込み条件を付け忘れない。** `countQuery()` は結果取得とは
  別のSQLなので、片方だけ絞ると一覧と画面上部の件数が食い違う
  （実際に会議名の絞り込みが件数に効いておらず、2,594件と557件が入れ替わっていた）。
  FTS・争点語・2文字語の**3経路すべて**にある。
  → 件数と月別（`monthlyQuery`）は `hitSource()` が組む FROM と WHERE を共有している。
  **絞り込みを足すときに直すのは `hitSource()` と `searchQuery()` の2か所**
- **まだ無い `<option>` の値を `select.value` に入れても選択されない。**
  会議名の一覧はDBから非同期で来るので、URLから条件を復元するときは
  その会議名の `<option>` を先に自分で足す
- **検索の開始ごとに世代番号を進めて、古い結果を捨てる。** 検索の速さは語で
  大きく変わるので、重い検索の裏で条件を変えると前の結果が後から混ざる
- **`snippet()` のマーカーに `<mark>` を直接入れない。** 本文は会議録そのままで
  `<` や `&` が入りうる。`char(1)/char(2)` で受けて、HTMLエスケープしてから置き換える
- **`site/src/lib/format.ts` から `db.ts` を import しない。** format.ts は
  `.astro` のフロントマター（ビルド時のNode側）からも読む。db.ts は
  sql.js-httpvfs に依存していてブラウザでしか動かないので、
  import が1本でも通ると SSR が落ちる。`operator.ts` も同じ
- **`query.ts` に sql.js-httpvfs を持ち込まない。** 1本でも通るとテストが動かなくなる
- **遅いのはヒット件数ではなく検索語の長さ。** ヒット14件の
  「デジタル田園都市国家構想」が、ヒット2,864件の「安全保障」の2.4倍遅い
- **争点語リストにある語は FTS を使わない。** `topic_hit` を引くほうが3.3倍速い

## R2 での配信

- **R2 にカスタムドメインを付けただけではキャッシュされない。** Cloudflare は
  **拡張子で判定**していて `.db` も `.json` も既定の対象外（`cf-cache-status: DYNAMIC`）。
  **Cache Rule が要る**。実測で **RTT 77ms → 8ms**
- **`MISS` は1回でオブジェクト全体をエッジに載せる。** 以後は未読の位置でも 8ms
- **無料プランのキャッシュ上限は1ファイル 512MB。**
  **超えたDBは黙ってキャッシュされなくなる**（エラーは出ない。RTT が 8ms → 77ms に戻り、
  待ち時間はリクエスト数×RTT なので検索が実質10倍遅くなる）。
  年で割っていたときの最大は 419MB で余裕が無く、いまは半期で割って最大 364MB。
  日次が `manifest.json` を見て 480MB で落とす
- **Edge TTL を固定値にしない。** アップロード時の `cache-control` に任せる。
  固定すると目録の更新が反映されない
- **DBを先に、目録を後に上げる。** 逆にすると、まだ無いDBをサイトが引きにいく
- **手で Pages に上げるときは `PUBLIC_DB_BASE` を必ず付ける。** 付け忘れると
  `/db`（開発用の相対パス）を指した `dist` ができ、**DBを引けないサイトが本番に載る**。
  エラーも出ない
- **`manifest.json` を失うと引き先が分からなくなる。** ファイル名は目録の記載を使う
  （規則で組み立てていない）ので、目録が壊れると検索が丸ごと止まる。
  日次は R2 の目録を復元してから走り、**手元に無い期間の記載を引き継ぐ**
- **★ `Origin` を付けずに公開URLを引かない**（2026-08-21 に踏んだ）。
  R2 は **`Origin` の付いた要求にだけ** CORS ヘッダを返し、応答に `Vary: Origin` を
  付けない。**`Origin` 無しの要求が先にエッジのキャッシュを埋めると、
  `Access-Control-Allow-Origin` の無い応答が全ブラウザに配られる。**
  目録で起きるとサイトが丸ごと止まる（`Failed to fetch`）。
  発生源は**検算そのもの**だった — 日次は「配る → 検算する」の順で、
  `verify_published.py`（Python の `urllib`）が `Origin` を送っていなかったため、
  **デプロイのたびに5分間の穴が開いていた**（目録は `max-age=300`）。
  いまは `Origin` を付けて引き、**返ってきた CORS ヘッダまで見る**。
  サイト側にも保険がある（`db.ts` は目録の取得に失敗したらURLを変えて1度だけ引き直す）

## 公開まわり（セキュリティ・コスト）

- **★クエリ文字列でキャッシュを素通りできる（未解決）。** `?v=...&junk=N` の N を
  変えるだけで別キーになり、**いくらでも MISS を作れる**（実測で確認）。MISS は
  R2 の `GetObject`（Class B・月1,000万まで無料）に届くので、**課金を外から積み増せる**。
  **正攻法（Cache Key を `v` だけに絞る）は Enterprise 限定で、free では塞げない。**
  取れる手と、叩かれたときの手順は `docs/PIPELINE.md` 手順3.5 の囲みにまとめてある。
  **Rate limiting の閾値を下げすぎないこと** — 6年検索は1回で500〜1,000リクエストの束なので、
  10秒あたり2,000未満にすると普通の利用者を弾く
- **`_headers` の CSP を触ったら実機で確かめる。** 壊れてもエラーが出ず、
  **機能だけ静かに消える**（`script-src 'self'` を入れた時点でメールのコピーボタンが消えた）
- **`astro.config.mjs` の `inlineStylesheets: "never"` と `vite.build.assetsInlineLimit: 0`
  を戻さない。** 戻すと Astro が小さいスクリプトをHTMLに直接埋め、CSP に弾かれる
- **`connect-src` に年DBのホストが要る。** `PUBLIC_DB_BASE` を変えたら `_headers` も変える
- **★ワークフローに `pull_request_target` を使わない。** public リポジトリで
  **fork のコードに secrets を渡してしまう唯一の経路**。CI を足すなら `pull_request`
  （fork からのトークンは読み取り専用になる）。いまの `daily.yml` は
  `schedule` と `workflow_dispatch` だけなので、この穴は無い
- **R2 の APIキーはバケット限定の Object Read & Write に留める。** アカウント管理権限を
  付けない。漏れたときに書き換えられる範囲がそのまま被害の範囲になる
- **★Web Analytics の RUM を「有効にする」（自動挿入）にしない。** Cloudflare が
  **エッジでビーコンのタグをHTMLに挿す**ので、リポジトリ側の `analytics` が `false` でも
  計測が始まる ＝ **公開中の `/privacy` が黙って嘘になる。** 必ず
  **「JS スニペットのインストールで有効にする」**にして、タグは `Base.astro` から出す。
  やめるときは `operator.ts` を `false` にするのと**同時にダッシュボードも「無効にする」へ**。
  **入口は2か所ある**（片方だけ切っても復活する）:
  Analytics & Logs → Web Analytics → サイトを管理 → RUM と、
  Workers & Pages → kokkai-timeline → **メトリクス画面の「Web 分析」**。
  後者は `無効です` のまま（2026-08-16 確認）。**「有効にする」を押さないこと**
- **★その自動挿入は、CSP を足した瞬間に動き出す。** 2026-08-16 に実際にこうなっていた:
  自動挿入でタグは入っていたが、`script-src` に `static.cloudflareinsights.com` が
  無かったのでブラウザが止めていて、ダッシュボードは14日間ずっと0だった。
  **CSP が実質のオフスイッチとして働いていた**ので、許可リストに1行足すだけの変更を
  配った時点で、コードを何も変えないまま計測が始まるところだった。
  **「CSP に足すだけだから無害」は成り立たない** — 何かがもう待っているかもしれない。
  配る前に本番のHTMLを見ること（`Invoke-WebRequest` で `cloudflareinsights` を探すだけでよい）
- **計測値の送り先は `cloudflareinsights.com` へ直接。** 同一オリジンの `/cdn-cgi/rum`
  ではない（2026-08-16 実測）。**`connect-src` から落とすと、タグは読まれるのに
  数字が入らない**（しかもエラーは `/privacy` を見ている人には見えない）

## 名寄せ

- **突合の単位は `(発言者, 読み, 会派)`。** 読みだけだと同姓同名が1行に潰れて分離できなくなる
- **`speakerYomi` が第一キー。** 会議録は「あべ俊子」「早稲田ゆき」のような通称を使うので、
  漢字表記だけで突合すると落ちる
- **Wikidata の `kana`(P1814) は空白入り**（7,844人が `'みき ぶきち'` 形式）。
  NFKC → カタカナ→ひらがな → 空白除去、の正規化をしないと**1件もマッチしない**
- **`data/party_map.json` を推測で埋めない。** 誤った対応表は同姓同名を**誤って分離する**ため、
  無記入より有害。判断がつかない会派は空リストにする
- **任期(P580)は付与率13.7%で当てにならない。** 同姓同名の分離は会派が最も強い信号
- **院は分離に使えない。** 大臣・副大臣は他院の委員会にも出るし、党首討論は `両院` になる
- **`party = '無所属'` と `party IS NULL` を混ぜない。** 前者は「政党に所属していないと
  分かっている」、後者は「特定できていない」

## Wikidata SPARQL

- **ラベルの全走査（`CONTAINS` で役職を探す）はエンドポイントが502/504を返す。**
  役職QIDは `wbsearchentities`（検索API）で特定する。
  衆議院議員 `Q17506823` / 参議院議員 `Q14552828`
- 人物属性と任期は**別クエリに分ける**。1本にまとめると OPTIONAL の直積で行数が爆発する
- User-Agent を明示しないと403

## 争点語

- **`data/topics.json` は運営の編集方針そのもの。** 何を争点として扱うかは判断が要る。
  **「もっと語を増やしたい」への答えは頻出語レイヤー**（[ROADMAP.md](ROADMAP.md)）であって、ここではない
- **★英数字は全角で書く。会議録は半角を1文字も使っていない。**
  半角で書くと**黙って0件になる**（初版の `生成AI` `LGBT` が実際に0件だった）
- **地名を争点語にしない。** 会派比較すると「その地名に言及した率」になって争点にならない
- **語を互いに部分文字列にしない。** `夫婦別姓` と `選択的夫婦別姓` を並べると二重に数える。
  同じ争点の別表記は `variants` に入れる。ただし**警告は1つの争点の中だけ**を見る。
  争点どうしの包含（`憲法`⊃`憲法改正`、`安全保障`⊃`経済安全保障`）は残すと決めた分
- **`id` は不変。並び順から採らない**（2026-08-21 にそう直した）。以前は `enumerate` で
  振っていたので、語を1つ差し込むだけで以降の `topic_id` が全部ずれ、
  `/topic/<id>` が**別の争点の発言を黙って出していた**。いまは `topics.json` に書く。
  **消した id は再利用しない**（配信済みDBに残る `topic_hit` を別の争点として引く）
- **語を足すのに全期間のDBの作り直しは要らない。** 配信済みDBが持っていない語は
  `indexed` が偽になり、サイトが普通の検索経路（`word` / FTS）で出す。
  **作り直しが要るのは `variants` を足したときと `term` を書き直したとき**
  （[PIPELINE.md](PIPELINE.md)「争点語を変えるとき」）
- **`term` を書き直したら、その id は全期間を作り直すまで `topic_hit` を使わない。**
  配信済みDBは**古い語**のヒットを持っているので、放っておくと新しい語の名前で
  古い語の発言が出る。目録の指紋がずれた時点で全部が検索経路に落ちる（遅いが正しい）
- **1文字・ひらがなだけ・文字種をまたぐ2文字を争点語にしない**（`お金` `ため`）。
  `topic_hit` に載るまでの間、**発言一覧が空になる**（2文字の索引は漢字・カタカナ・
  全角英数の連続の中しか切らない）。`build_topics.py` が読み込み時に警告する
- **候補は頻度上位ではなく増減で見る。両端ではなくピーク年と中央値を比べる**
- **機械抽出に人名が混ざる。**「〜議員」「〜大臣」で終わる語は姓の照合を待たずに落とす
  （姓が1文字だと照合をすり抜けて「簗議員」が漏れた）。
  取り切れない分は `data/topic_denylist.json` に1行足して消す

## 頻出語（`build_frequent.py`）

全部 2026-08-06 に実測して踏んだもの。

- **★選定と集計で数え方が違う。変えるときは両方を見ること。**
  選定は「自立した run」、集計は「部分文字列の発言数」。
  **選定を部分文字列にすると断片が上位を占める**（`国務大`←国務大臣、`御異議`）。
  **集計を run 単位にすると検索結果と数が合わない**（検索は `word_hit` も FTS も
  部分文字列で当てるので、「グラフは1,200件なのに検索は300件」になる）。
  `build_db.py` の2文字語索引が「拾うのは部分文字列」なのと同じ理由
- **2文字の下限（`--min-standalone2` 既定5）を3〜4文字（既定50）と揃えない。**
  以前は2文字を `words.json`（`--min-df 5`）から採っていたので、
  そこを揃えると**一覧に載る2文字語が黙って減る**。
  定型語（委員・大臣・質問…）は `build_topics.STOPWORDS` が落とすので別リストは要らない
- **頻度順に並べない。** 実測の上位は `国務大` `日本` `重要` `関係` `指摘` `是非`。
  burst（ピーク年 ÷ 中央値の年）で並べると、コロナ・統一教会・裏金・中東が
  それぞれの時期の語として出る
- **短い語と長い語が並ぶ。** `変異`/`変異株`、`参政`/`参政党`、`規正`/`規正法`。
  短いほうの出現の75%以上が長いほうの中なら落とす（`--dup-ratio`）
- **2文字の全角ラテンは略語の断片になる。** `ＯＴＣ`→`ＴＣ`、`ＪＢＩＣ`→`ＢＩ`。
  自立した発言数と部分文字列の件数の比で見分ける（どちらも `build_frequent.py` が数える）。
  `ＡＩ` は 5,394/5,412 でほぼ一致するが、断片は自立して出てこない
- **語の途中に平仮名が入るものは断片が残る**（`まん延防止`→`延防止`、`目詰まり`→`目詰`）。
  機械的には直せないので `data/topic_denylist.json` に1行足す
- **会派の内訳を全語に持たせない。** 実測で 500語 × 20会派 × 64月 = **1.6MB**
  （語だけなら115KB）。必要になったら別ファイルにして上位数十語だけ
- **★会期を月の合算で作らない。** 会期は月境界で始まらない（第204回は 2021-01-18 開会で、
  同じ2021年1月に第203回が同居する）。足し合わせると境目の発言が隣の会期に混ざる。
  `build_frequent.py` が会期ごとに直接数えている（500語×11会期で +23KB）
- **会期の一覧に発言の少ない会期を入れない。** 第220回は議員発言が**191件**しかなく、
  並べても首班指名と議長選出の手続き語しか出ない。既定は3,000件未満を除外
- **会期での並びも件数順にしない。** その会期の出現率 ÷ 全期間の出現率で並べる。
  件数順にすると `日本` `国民` `経済` が並んで、どの会期を選んでも同じ顔になる。
  **件数の下限（既定30件）も要る** — 3件が9件になっただけの語が3倍として上に来る

## ★ インラインの `style` 属性は CSP に消される

**`style-src 'self'`（`'unsafe-inline'` 無し）なので、`style="…"` は黙って無視される。**
エラーも警告も出ず、**見た目だけが静かに間違う**。`<script>` の埋め込みで一度踏んだのと
同じ穴で（`site/public/_headers`）、こちらは属性版。

実際に踏んだもの（2026-08-10 に両方直した）:

- **`/topic/<id>` の会派バーが全部同じ長さだった。** `style="width: 58.7%"` が効かず、
  20本すべてが満杯の240pxで描かれていた。**公開時からずっとそうなっていた**
- 議員ページの凡例の色見本が**すべて無色**だった（`style="background:…"`）

**代わりに SVG の presentation attribute（`fill` `width`）を使う。**
CSP の対象外なので効く。実際、同じページの棒グラフは最初から正しく塗れていた。

- 幅を出すなら `viewBox="0 0 100 6"` の `<rect width="58.7">`。`width` がそのまま％になる
- 色を出すなら `<rect fill="var(--cat-1)">`。CSS変数もそのまま通る
- 動的な値を CSS 変数で渡すのも**不可**（`style="--w: 58%"` も style 属性なので消える）

**dev サーバも `astro preview` も `_headers` を適用しない。** だから開発中は正しく見える。
**CSP 付きで dist を配って確かめること。** `site/test/stacked-chart.test.ts` に
「`style=` を出さない」テストを入れてあるが、それは `chart.ts` の範囲しか守らない。

## 集計と表示

- **分母（その月の発言数）で割らずにグラフにしない。** 国会は通年で開いていないので、
  割らないと「開催日数が多い月」が争点に見える
  - **例外は検索結果のグラフだけ**（`/search`）。既定は件数で、切り替えで率にする。
    件数のときは figcaption で「国会が長く開かれた月ほど大きく出る」と必ず断る。
    **同じ語で結論が逆になる**（実測・2025年: `安全保障` は件数だと1月が最低の68件、
    率だと1月が 74.9 で突出。1月の議員発言は908件しかない）
  - **会議名で絞ったら分母も会議名で絞る。** 全体で割ると率が小さく出る。
    分母は `topics.json` の `meeting_totals`（配ってある。ブラウザから数えると
    `speaker_kind` の索引を端から端まで舐めて 80ms/期間）
- **週次トレンドをカレンダー週で区切らない。** 実測で直近8週のうち2週が発言不足で
  集計にならなかった。発言のあった日を5日ずつまとめている
- **`trending.json` の中身は「その週に審議された法案の専門用語」が主で、
  「今週の争点」ではない。** 表示の言葉を誇張しない
- **議員ごとの発言数の分布を出さない。** 発言数は委員会の所属と役職で決まるので、
  並べると事実上の議員評価になる（[SCOPE.md](SCOPE.md)）。**会派ごとの分布は出す**
